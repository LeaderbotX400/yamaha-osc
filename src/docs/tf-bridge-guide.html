Overview

One Python service, one job: listen for OSC on the network and drive the console. Everything you fire from QLab is a plain OSC message to UDP port 8000 on the Mac.

QLab, the bridge, and the console share the booth Mac's wired connection. QLab sends OSC to 127.0.0.1:8000 (loopback — the bridge is on the same machine); the bridge holds one long-lived TCP connection to the console at 192.168.50.2:49280 and translates each message into Yamaha's Remote Control Protocol (RCP).

Two dialects, one service

A rich new /ch · /mix · /dca … grammar for faders, fades, sends and labels — and the original /tf mute/scene addresses, kept working so existing show files need no changes.

Built for the booth

Blocking sockets (proven rock-solid on this Mac), a reconnect loop, and a guard that only talks to the console when the Mac is actually on the 192.168.50.x network.

A “safety catch” you can rely on. The bridge refuses to send anything unless one of the Mac's own IP addresses is on the 192.168.50.* subnet. Off the console network, cues are silently dropped rather than sent somewhere unexpected.

Using it from QLab

Every bridge cue is a QLab Network cue whose destination is the TF3 patch and whose message is one line from the dictionary below.

The one-time setup (already done on the booth Mac)

Settings → Network → OSC has a UDP patch named TF3 pointed at 127.0.0.1 port 8000, kept first in the list. Because it's first, new Network cues default to it — no per-cue destination fiddling.

Making a cue

  1. Add a Network cue (or duplicate one from the TF BRIDGE TEMPLATES group in TF Bridge Template.qlab5).
  2. Confirm its Destination is TF3.
  3. Set the message to one line below, e.g. /ch/5/fader -6.
  4. Name and number the cue for your show.
Quoting matters. QLab splits the message on spaces. A text value that contains a space must be quoted: /ch/1/name "Lead Vox" sends one string; without quotes QLab sends two. Numbers like -6 or 2000 are sent as numbers — the bridge accepts either.

A ready-made palette

The TF BRIDGE TEMPLATES group ships one labelled cue per function — copy a cue, change the channel number and value, done. It's regenerated by bridge/qlab/generate.applescript if you ever want to rebuild or extend it.

Two ways to fade a channel

Both work — pick per cue:

Bridge fade

One message — /ch/1/fade -30 2000 cosine — and the bridge runs the ramp. The console keeps moving even if QLab is busy. Fades to −∞ are fine.

QLab-native fade

A Network cue with message /ch/1/fader #v#, Fade → 1D Fade, From/To in dB and a Duration. QLab runs the ramp (with its curve editor and live preview) and sends the interpolated levels. Can't reach −∞ this way.

OSC dictionary

The complete address set the bridge understands. New-grammar addresses are teal; legacy /tf addresses are amber. Channel and bus numbers are 1-based, matching the console surface (channel 1 on the desk = /ch/1/…).

Conventions

Four things recur across every address: how levels are written, how fades curve, how you pick more than one channel at once, and the −∞ sentinel.

Levels are in dB

A fader/level argument is decibels: 0, -6, -6.5, 3.2. The ceiling is +10 dB; the floor is −∞, written -inf (or any value ≤ about −327 dB). Internally the console works in hundredths of a dB — the bridge does that conversion for you (e.g. -6 → raw -600, -inf → -32768). If you ever need raw units directly, use /…/fader/raw.

Fades ride a curve

A fade takes a target dB and a duration in milliseconds, then steps the fader at 30 Hz until it lands exactly on target. A later fade or fader on the same target cancels the one in flight (last writer wins). Curve names:

CurveAliasesFeel
linearlinConstant rate — the default.
cosinecos · s · scurveEases in and out — natural for level moves.
expexponentialSlow start, fast finish (t²).

Selectors pick one or many

Where an address has a <sel>, you can address a single number, a range, or a comma list — all in one cue:

SelectorMeans
5Channel 5
1-8Channels 1 through 8
1,3,5Channels 1, 3 and 5
allEvery channel on that strip

Out-of-range numbers are dropped; the console ignores anything it doesn't have.

New grammar /ch · /mix · /dca …

Pattern: /<strip>/<sel>/<param> <args>. These are direct — fired immediately, last-writer-wins. (Only /tf mutes and scene recalls are re-asserted after a scene; see How it behaves.)

AddressArgsEffect
/<strip>/<sel>/fader<dB> or -infSet fader level in dB. Ceiling +10 dB.
/<strip>/<sel>/fader/raw<raw>Set level in raw units (hundredths of dB; −32768 = −∞).
/<strip>/<sel>/fade<dB> <ms> [curve] [fromDB]Ramp to dB over ms. A later move cancels it.
/<strip>/<sel>/on0 | 1Channel on/off (1 = on).
/<strip>/<sel>/mute0 | 1Mute (1 = muted = fader off).
/<strip>/<sel>/name"text"Set the channel name (quote if it has spaces).
/<strip>/<sel>/colorBlueSet the label colour (see the swatches below).

Examples

/ch/5/fader -6           # input 5 to −6 dB
/ch/5/fader -inf         # input 5 to −∞
/ch/1-8/mute 1           # mute inputs 1..8 in one cue
/ch/5/fade -30 2000 cosine   # glide to −30 dB over 2 s
/ch/5/name "Lead Vox"    # rename channel 5

/st/1/fader -3           # stereo master to −3 dB

Sends

A send routes one strip to a destination bus. Input-type strips send to mix; output-type strips (mix/stereo/mono) send to matrix. Destination numbers are 1-based.

AddressArgsEffect
/<strip>/<sel>/send/mix/<dest>/fader<dB>Input → mix send level.
/<strip>/<sel>/send/mix/<dest>/on0 | 1Input → mix send on/off.
/<strip>/<sel>/send/mix/<dest>/fade<dB> <ms> [curve]Ramp a send level.
/<strip>/<sel>/send/mtrx/<dest>/…same leavesOutput strips (mix/st/mono) → matrix instead.
 
/ch/1/send/mix/3/fader -12   # input 1 into mix 3 at −12 dB
/ch/1/send/mix/3/on 1        # turn that send on
/mix/2/send/mtrx/1/fader -6  # mix 2 into matrix 1
Using the wrong bus word for a strip (e.g. asking an input to send to mtrx) is rejected and logged, not sent.

/scene/recalla | b   <n>Recall scene n (0–99) from bank A or B. stateful — mutes re-assert on top.

Legacy /tf grammar

The original addresses, unchanged — existing show cues keep working. These mutes are stateful: the bridge remembers what you muted and re-asserts it after a scene recall.

AddressArgsEffect
/tf/mute<tokens…>Mute the listed things (token grammar below).
/tf/unmute<tokens…>Unmute the same tokens.
/tf/sceneA<n> | B<n>Recall a scene (e.g. A12); mutes re-assert afterward.

Mute token grammar

Tokens are space- or comma-separated, and ranges/lists/all work throughout (/tf/mute 1, 4, 7-12, 15):

TokenTargets
1 · 7-12 · allInput channels (bare numbers)
aux <n>Mix buses — stereo-pair aware (aux 9 covers the 9/10 pair; aux 9/10 also works)
matrix <n>Matrices 1–4
dca <n>DCA groups 1–8 (writes both DCA + DcaCh)
fx1 · fx2FX returns (each covers its stereo pair)
st1 · st2Stereo input channels
masterStereo master (L/R)
subMono / sub master
 
/tf/mute 1, 4, 7-12, 15    # the real-world show syntax
/tf/mute all               # everything
/tf/mute aux 9  dca 1      # a mix pair and a DCA
/tf/unmute all
/tf/scene A05              # recall scene A05

How it behaves

The one distinction worth internalising: mutes are remembered, levels are not.

stateful Legacy /tf mutes & scenes

The bridge tracks what you've muted. Recall a scene and it re-applies those mutes on top of the freshly-loaded scene — so a channel you killed stays killed across a scene change.

direct New-grammar levels, fades, sends, /ch mutes

Fired straight to the console, last-writer-wins, and not re-asserted after a scene. Use these for moment-to-moment moves; use /tf mutes for state you want held through scene changes.

Fades are cancellable. Starting a new fade — or any direct fader write — on a target that's mid-fade cancels the old one cleanly and the new move wins. Concurrent fades on many channels are paced so the console never floods.

Connection handling

The bridge keeps one connection open and reconnects automatically if the console blips. On a fresh connection it re-syncs its remembered mute state. If the Mac isn't on the 192.168.50.x network, it parks in a NO_TF_NETWORK state and sends nothing until it is.

Running & operations

The bridge is plain Python 3 + python-osc, kept alive by a user launchd agent. No build step, no toolchain.

ThingWhere
Service (launchd)tf3.server  (~/Library/LaunchAgents/tf3.server.plist)
Script it runs~/Scripts/tf3.py  (holds the current bridge)
Original, for rollback~/Scripts/tf3.py.orig
Interpreter…/Python.framework/Versions/3.14/bin/python3

Restart / reload

launchctl bootout   gui/$(id -u)/tf3.server
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/tf3.server.plist
tail -f /tmp/tf3.out.log      # expect: "OSC server listening on 0.0.0.0:8000" then "TF CONNECTED"

Roll back to the old bridge

cp ~/Scripts/tf3.py.orig ~/Scripts/tf3.py
launchctl bootout   gui/$(id -u)/tf3.server
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/tf3.server.plist

Troubleshooting

SymptomLikely cause & fix
A cue does nothingCheck the cue's Destination is TF3 (→ 127.0.0.1:8000). A cue on the wrong patch goes nowhere. Watch /tmp/tf3.out.log — a received message logs a SEND: line.
Nothing works at allLog shows NO_TF_NETWORK → the Mac isn't on the console's wired network. Reconnect the cable / check the interface is on 192.168.50.x.
Log shows CONNECTING loopingConsole unreachable at 192.168.50.2:49280 — powered on? same switch? The bridge retries every 2 s and recovers on its own.
A name didn't takeMulti-word name wasn't quoted, so only the first word arrived. Use /ch/1/name "Two Words".
A colour didn't takeUse the exact capitalised name (Blue, SkyBlue). Bad colours are logged, not sent.
Mute came back after a sceneExpected for /tf mutes — they're re-asserted on top of recalled scenes. Use a new-grammar /ch/N/mute if you want a non-sticky mute.
Every received message and console write is logged with a SEND: line, and state changes log DESIRED: / SYNC: / SCENE:. When in doubt, tail -f /tmp/tf3.out.log and fire the cue.
